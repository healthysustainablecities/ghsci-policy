This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

GHSCI Policy is a web app for the 1000 Cities Challenge (Global Observatory of Healthy and Sustainable Cities). Users upload a completed policy checklist audit (Excel `.xlsx`) or fill in an online form; the app scores their city's policy indicators and generates downloadable, multi-language PDF reports. Frontend is React 18 + TypeScript + Vite; backend is AWS Amplify Gen 2 (Cognito auth, AppSync GraphQL, DynamoDB, S3, Lambda).

## Commands

```
npm run dev            # Vite dev server (http://localhost:5173)
npm run sandbox        # Amplify sandbox backend (npx ampx sandbox)
npm run dev:full       # Both concurrently
sandbox.bat            # Sandbox using AWS_PROFILE from .env.local (Windows)
npm run build          # tsc && vite build
npm run lint           # eslint, --max-warnings 0
```

There is no test suite. `.env.local` holds `AWS_PROFILE` and `VITE_GEONAMES_USERNAME`. Production deploys via AWS Amplify hosting using `amplify.yml` (`ampx pipeline-deploy` + `npm run build`).

## Processing pipeline (the core architecture)

Two entry paths converge on one Python Lambda (`amplify/functions/process-policy-report/`):

1. **xlsx upload**: Frontend uploads to S3 at `public/{username}/{filename}.xlsx` and creates a `PolicyReport` record (status `UPLOADED`). An EventBridge rule (defined in `amplify/backend.ts`) fires the Python Lambda on any `.xlsx` object creation. Re-processing/regeneration goes through the `triggerReportProcessing` GraphQL mutation instead, handled by `amplify/functions/trigger-processing/handler.ts`, which async-invokes the same Python Lambda with a synthetic S3-event payload.
2. **Online form**: The `submitPolicyForm` mutation routes through the same trigger-processing Lambda with `formData` and a `syntheticKey` (there is no real S3 xlsx file in this path).

The Python `handler.py` distinguishes three event shapes: `formData` present → form path; `Records` → direct/synthetic S3 event; `source: aws.s3` + `detail` → EventBridge. It parses the checklist, updates the DynamoDB record's status (`UPLOADED → PROCESSING → COMPLETED / FAILED / INCOMPLETE`), and writes PDFs alongside the source file under `private/{identityId}/reports/` (per-user, IAM-enforced via `allow.entity('identity')`; legacy objects under `public/...` remain readable during migration — see `STORAGE_MIGRATION.md`). `pdfUrls` on the record is a JSON dict mapping language → S3 key. The frontend tracks status in real time via `observeQuery` subscription; `App.tsx` deliberately blocks subscription updates from downgrading a terminal status (COMPLETED/FAILED) unless the user explicitly triggered regeneration (`processingOverrideIds`).

The Lambda looks up DynamoDB records by scanning on `fileKey` with retries, because the frontend creates the record around the same time the S3 event fires — don't assume the record exists on first attempt.

### Why the Python Lambda is raw CDK

`backend.ts` defines the Python Lambda with raw CDK (`aws-cdk-lib/aws-lambda` `Function`) inside the **data stack**, not `defineFunction`, and enables EventBridge notifications rather than direct S3→Lambda triggers. Both choices avoid circular dependencies between the storage and data stacks — preserve this pattern when modifying the backend.

### ghsci.py and compatibility with global-indicators

This app is an extension of the open-source GHSCI toolkit (healthysustainablecities/global-indicators). Functions in `handler.py` and `ghsci.py` are shared with that external project's workflow — **keep changes to these files additive and signature-compatible** (optional kwargs with defaults; never rename/remove functions or change required parameters), and avoid modifying `ghsci.py` unless the change is intended to flow back upstream.

`amplify/functions/process-policy-report/ghsci.py` (~2500 lines) is the scoring and PDF-generation engine, adapted from that toolkit. It parses the checklist Excel, computes presence/quality scores per policy indicator (criteria per measure: identified, aligns, measurable), validates the checklist, and renders PDFs with fpdf2 using fonts/assets from `configuration/`. Report layout is driven by `_report_configuration.xlsx`.

### Python dependencies are vendored

The Lambda's dependencies live committed in `amplify/functions/process-policy-report/lib/` as manylinux2014_x86_64 wheels for Python 3.13 (Lambda runtime). They are regenerated by the GitHub Action `.github/workflows/install-lambda-deps.yml` when `requirements.txt` changes on main, or locally via `install-deps.ps1`. Never `pip install` into `lib/` with Windows-native wheels.

## Data model (amplify/data/resource.ts)

- `PolicyReport` — owner-authorized; holds file metadata, status enum, `reportConfig` / `initialReportConfig` (JSON, for customization and revert), `policyData` (parsed scores), `pdfUrls`.
- `Feedback` — authenticated users create/read; `Admins` Cognito group has full access (dev responses via `devComment` fields).
- `policyChat` — Amplify AI conversation route backed by Bedrock (Claude), for policy-analysis chat over checklist data.
- Mutations `triggerReportProcessing` and `submitPolicyForm` both handled by the trigger-processing function.

## Frontend notes

- `src/App.tsx` — auth shell, report list state, subscription merge logic, example-report loader.
- `src/components/PolicyForm.tsx` (~1800 lines) — the online checklist form alternative to xlsx upload.
- `src/components/ReportSettings.tsx` — edit `reportConfig` (images, languages, context text) and trigger regeneration.
- `src/components/ReportsList.tsx` — report cards, PDF downloads per language, delete/regenerate.
- Storage: new objects go to `private/{identityId}/...` (built via `src/lib/storagePaths.ts`; IAM-enforced per user). Legacy `public/*` is read-only for authenticated users during migration. Cognito group members (e.g. `Admins`) assume the group's IAM role instead of the default authenticated role — user-facing IAM grants in `backend.ts` must be attached to **both** roles.
